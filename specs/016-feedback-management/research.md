# Phase 0 Research: Feedback Management

**Feature**: `016-feedback-management` | **Date**: 2026-09-14

Depends on `001-company-role-user-setup` (`companies`/`users`, RLS/session-variable mechanism), `002-registration-login-jwt-auth` (JWT claims, `@CurrentUser()`), and `011-audit-logs-product-order-payment` (`fn_audit_log()`, the generic audit trigger this feature reuses). No `[NEEDS CLARIFICATION]` markers remained in `spec.md`, so this document resolves implementation-pattern questions only.

## 1. Modeling the fixed Category list as a `text` + `CHECK`, not a lookup table

- **Decision**: `feedback.category` is a `text NOT NULL` column with a `CHECK` constraint against the fixed six-value set (`app_experience`, `food_order_quality`, `payment_issue`, `pickup_experience`, `suggestion`, `other`), paired in TypeScript with a `const` object + derived union type per `coding_standard.md` §2 (the same pattern already used for `order.status`/`roles.name`) — not a foreign key to a new lookup table, and explicitly not a reuse of the existing per-tenant `categories` table from `001`.
- **Rationale**: The spec's Key Entities section is explicit that this is a fixed, platform-wide, non-user-manageable classification list — the opposite of `001`'s `categories` table, which is per-tenant master data an admin can CRUD. Reusing `001`'s `categories` table would conflate two unrelated concepts that already share a confusingly similar name (CLAUDE.md's own "Category vs Department vs Role" section exists precisely to warn against this kind of mixing). A `CHECK` constraint keeps the valid-value set enforced at the database layer without standing up a table, migration seed data, and an admin-CRUD surface for six values that never change per this spec.
- **Alternatives considered**: A new `feedback_categories` lookup table — rejected as unwarranted ceremony for a fixed enum with no admin-management requirement in the spec; a Postgres native `ENUM` type — rejected per `coding_standard.md` §2's explicit rule against DB-level/TS `enum` for domain values that are just as well expressed as `text` + `CHECK`, since adding a seventh category later would require an `ALTER TYPE` migration instead of a one-line `CHECK` constraint edit.

## 2. Reusing `011`'s `fn_audit_log()` trigger for `feedback` mutations

- **Decision**: Attach the existing generic `fn_audit_log()` function to `feedback` via `CREATE TRIGGER audit_feedback AFTER INSERT OR UPDATE ON feedback FOR EACH ROW EXECUTE FUNCTION fn_audit_log();` in this feature's migration — extending the mechanism to a fourth table rather than building anything new.
- **Rationale**: Inspection of the actual `20260906210000_audit_logs` migration shows `fn_audit_log()` is genuinely table-agnostic for company_id resolution — every table other than `payment_attempts` (which has no `company_id` column of its own) falls through to `v_company_id := NEW."company_id"`, which is exactly `feedback`'s shape. The only table-specific branch (`TG_TABLE_NAME = 'products'`, classifying a soft-delete as a `'removed'` action) is additive and simply doesn't fire for any other table, including `feedback` — a `feedback.is_deleted` transition (not exercised by this feature's own endpoints, which have no delete path) would be logged as a generic `'updated'` action, which is harmless and consistent with how `orders`/`payment_attempts` are already handled today. Getting Company Admin's `new → resolved` resolution action a full changed-fields audit trail for free — with zero application-level logging code — is exactly the payoff `011`'s design intended, and matches CLAUDE.md's blanket "every mutation of a business-critical table is recorded in `audit_logs` automatically via DB trigger" framing.
- **Alternatives considered**: Leaving `feedback` outside the trigger entirely, like `companies`/`roles`/`categories`/`departments`/`users` currently are (per `011`'s own explicit scope note limiting itself to `products`/`orders`/`payment_attempts`) — rejected because those tables were excluded because `011` scoped itself narrowly at the time, not because they're unsuited to the mechanism; `feedback`'s status-resolution action is precisely the kind of "who changed what, when" event this trigger exists to capture automatically, and the fourth-table attachment is a pure additive change (a `CREATE TRIGGER` statement plus a doc-comment update on the `AuditLog` Prisma model, which currently says "attached to those three tables" and will need a one-line correction as part of this feature's implementation — noted here so it isn't missed, not treated as a design blocker).

## 3. Not duplicating the submitter's email onto the `feedback` row

- **Decision**: `feedback` stores only a `contact_requested boolean` flag — never a copy of the submitter's email. When Company Admin requests a feedback item's detail (`GET /tenant/feedback/{id}`) and `contact_requested = true`, the API resolves the email at read time via a join to `users.email` (through the existing `created_by` foreign key) and includes it in the response as `contact_email`; the list endpoint omits it (flag only, per spec SC-005's "detail view," not the list).
- **Rationale**: The spec's own framing — "shows their registered email (read-only, already known — no need to ask again)" — is explicit that this is the user's *existing* profile email, not new data being captured. Storing a second copy on the feedback row would let it silently go stale if the user later changes their email via `007`'s profile-edit flow, with no mechanism in this feature to keep it in sync. A read-time join has no such staleness risk and costs nothing extra, since every feedback row already has `created_by` as a foreign key to `users`.
- **Alternatives considered**: Snapshotting the email onto the row at submission time (matching how `006`'s orders snapshot product name/price at checkout) — rejected; that pattern exists specifically because an order's line items must reflect the price *at the time of purchase* even if the product changes later (FR-11.3 in `02-PRD.md`), which is a deliberate historical-record requirement. Nothing in this spec calls for "the email as it was at submission time" as a business rule — the opposite is implied ("already known", i.e. current on-file contact info is what matters for an admin follow-up).

## 4. `feedback.user_id` as a domain column, separate from `created_by`/`updated_by`

- **Decision**: `feedback` carries both a `user_id` column (the submitter — who this feedback is *about*/*from*, immutable after creation) and the standard nullable `created_by`/`updated_by` audit columns every table in this schema carries, mirroring the exact pattern already used by `orders` (`Order.userId` alongside `Order.createdBy`/`Order.updatedBy` in `schema.prisma`).
- **Rationale**: Even though `user_id` and `created_by` hold the same value at creation time for this feature (the submitter creates their own record — there's no "staff submits on a student's behalf" concept here), keeping them as separate columns matches the platform's own established convention for exactly this shape of table, avoids special-casing `feedback` relative to `orders`, and leaves room for `updated_by` to correctly diverge from `user_id` once Company Admin resolves the item (the resolving admin becomes `updated_by`, while `user_id` — the submitter — never changes).
- **Alternatives considered**: Collapsing to `created_by` only (no separate `user_id`) — rejected as inconsistent with `orders`' own precedent in this same schema, and it would make "who is this feedback from" a semantically overloaded read of an audit column rather than a first-class domain field.

## 5. `resolve` is a body-less, one-way transition — no separate un-resolve path

- **Decision**: `PATCH /tenant/feedback/{id}/resolve` takes no request body and moves `status` from `new` to `resolved` only. Calling it on an already-`resolved` item is a no-op success (`200`, unchanged), not an error. There is no endpoint to move a `resolved` item back to `new`.
- **Rationale**: The spec explicitly describes exactly two states with one direction of travel ("if the user creating feedback (new status), company_admin verify and make it resolve"), unlike `004`'s sold-out toggle (`PATCH .../soldout`) which is genuinely bidirectional and therefore needs a body carrying the target value. Treating a double-resolve as a harmless no-op rather than a `409 Conflict` avoids punishing an admin's accidental double-tap for a transition that has no real invalid-state risk (unlike, say, resolving an order payment twice, which `010` treats far more strictly because money is involved).
- **Alternatives considered**: Rejecting a resolve-on-already-resolved with `409` — rejected as needless strictness for a low-stakes, non-financial status field; adding an "in review" intermediate state — rejected, since the spec's Assumptions section explicitly commits to exactly two states for V1 and a third state would be scope creep not asked for.
